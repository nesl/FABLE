FABLE Experimental Plan
========================

Purpose
-------
This document defines the implementation, configuration, instrumentation, and execution work needed to complete the FABLE evaluation under a limited page budget.

The recommended main-paper evaluation is organized into four experiment blocks:

  E1. End-to-end effectiveness
  E2. Checkpoint-bounded planner quality
  E3. Dynamic evidence mechanisms
  E4. Real heterogeneous adaptation on Raspberry Pi + Jetson Orin + desktop

A small E5 control-plane scaling experiment should also be implemented if practical, even if it ultimately appears only in the appendix.

The intent is NOT to create a separate physical-testbed research question. The physical testbed strengthens the existing claims, especially adaptation to changing execution conditions.


======================================================================
0. Evaluation questions and intended paper story
======================================================================

RQ1 — End-to-end effectiveness
Question:
  Does deriving evidence-production work from the progress of each
  complex-event hypothesis preserve recognition while reducing
  unnecessary computation and communication?

Primary experiment:
  E1

Key comparison:
  B0 / B1 / B2 / B3 / B4 / FABLE


RQ2 — Checkpoint-bounded physical planning
Question:
  Given the current frontier, does jointly planning provider, source,
  representation, placement, transfer, and continuation choices through
  the next semantic checkpoint improve execution decisions relative to
  fixed or greedy realizations?

Primary experiment:
  E2

Key comparison:
  B2 / B4 / FABLE / O1 exhaustive checkpoint oracle


RQ3 — Adaptation to dynamic evidence and execution conditions
Question:
  Can FABLE change (a) what evidence-producing work is useful and
  (b) how/where that work executes as CE progress and operational
  conditions change?

Primary experiments:
  E3 + E4

E3 covers semantic/evidence dynamics:
  - spatial progression
  - retrospective evidence dependence
  - optional branch resolution/cancellation

E4 covers execution/resource dynamics:
  - real compute heterogeneity
  - compute contention
  - network/path degradation


======================================================================
1. Baseline definitions to implement consistently
======================================================================

B0 — Produce-All
  - Use the CE-authored provider chains.
  - Produce each task-relevant realization broadly across eligible nodes.
  - High-resource evidence-availability reference.
  - No frontier-based suppression of irrelevant work.

B1 — Static whole-event
  - One developer-authored source/provider/placement plan.
  - Physical choices remain fixed for the request.
  - No resource-triggered replanning.
  - No instance-specific frontier-driven physical adaptation.

B2 — Frontier-fixed
  - Use the current grounded frontier.
  - Only current frontier predicates create work.
  - Each predicate type has a fixed provider-chain realization.
  - No dynamic provider/representation/placement selection.

B3 — Task resource-adaptive
  - Maintain the full task-level evidence-producing work set for the CE request.
  - Reconfigure provider/placement choices on resource epochs.
  - Do NOT suppress, retarget, or create tasks based on the progress,
    resolved branches, or likely-next sensors of a particular CE hypothesis.
  - This is the closest approximation to conventional adaptive CEP/dataflow:
    adapt HOW the configured task executes, not WHAT instance-specific work exists.

B4 — Greedy frontier
  - Use the current grounded frontier.
  - Select each demand independently.
  - Greedy criteria may include immediate reuse, predicted completion,
    compute cost, and transfer cost.
  - No joint checkpoint-level search across demands.

FABLE
  - Use the current grounded frontier.
  - Jointly search physical realizations through the next semantic checkpoint.
  - Select source/provider/representation/placement/transfers/artifacts together.
  - Replan after semantic checkpoints and resource/network epochs.

O1 — Exhaustive checkpoint oracle
  - Enumerate all feasible alternatives for the same current checkpoint.
  - Offline only.
  - Used to measure bounded planner gap on tractable cases.


Implementation requirement:
  All policies MUST share:
    - identical CE definitions
    - identical provider implementations
    - identical primitive outputs/thresholds when using common-observation mode
    - identical node capacities and provider profiles for a given experiment
    - identical retention limits
    - identical network schedule
    - identical trace/event-time schedule
    - identical random seed where applicable

3. E1 — End-to-end effectiveness
======================================================================

Goal
----
Test whether frontier-derived execution preserves CE recognition while
reducing unnecessary evidence production.

Workloads
---------
Use the existing recommended evaluation corpus where applicable:

  - Vehicle convergence
  - Route convoy
  - Two-vehicle chase
  - Robbery with alarm
  - Vehicle rendezvous
  - Talking/rendezvous
  - Pass-follow-clear convoy
  - Three-visit stalking
  - Cross-sensor robbery

Target:
  Use all valid/recommended traces for which the compared policies are
  implemented and calibrated.

Policies
--------
  B0
  B1
  B2
  B3
  B4
  FABLE

Execution mode
--------------
Primary:
  end-to-end replay using real provider executions

Secondary/common-observation control:
  feed identical primitive observations to each policy to confirm that
  differences are due to orchestration rather than detector variation


Implementation tasks
--------------------
[ ] Finish B0 implementation and verify it truly produces the broad task-level evidence reference.
[ ] Finish/calibrate B1 plans for every included CE family.
[ ] Implement B2 fixed predicate->realization map.
[ ] Implement B3 full task-work-set + resource-epoch replanning.
[ ] Verify B3 does NOT use hypothesis frontier, branch resolution, or likely-next sensors.
[ ] Implement B4 per-demand greedy selector.
[ ] Freeze FABLE online ranking configuration.
[ ] Freeze common provider thresholds and provider versions.
[ ] Ensure matched resource accounting across policies.
[ ] Ensure failed/aborted policies are not rewarded with artificially low resource cost.

Configuration
-------------
Create one policy configuration per baseline, e.g.:

  configs/policies/b0_produce_all.yaml
  configs/policies/b1_static.yaml
  configs/policies/b2_frontier_fixed.yaml
  configs/policies/b3_task_adaptive.yaml
  configs/policies/b4_greedy_frontier.yaml
  configs/policies/fable.yaml

Create one experiment manifest:

  experiments/e1_end_to_end.yaml

Manifest should specify:
  traces
  policies
  deterministic replay
  fixed seed
  provider catalog
  retention limits
  nominal network
  nominal resource allocation
  output directory

Headline metrics
----------------
  recall
  timely recall
  detection delay
  CPU seconds
  GPU seconds
  transmitted bytes
  processed frames

Analysis
--------
Report:
  - full recognition result over completed positive runs
  - resource comparison on exact matched-correct trace cells
  - relative savings versus B0 and B1
  - difference between frontier-aware policies (B2/B4/FABLE)
  - B3 versus FABLE to isolate task-level resource adaptation from
    instance-progress-driven work selection

Main-paper output
-----------------
TABLE 1:
  Policy | Recall | Timely Recall/Delay | CPU | GPU | Network | Frames

4. E2 — Checkpoint-bounded planner quality
======================================================================

Goal
----
Test whether joint checkpoint planning improves decisions beyond fixed
or greedy frontier realizations, while remaining close to an exhaustive
oracle and keeping planning overhead practical.

Workload
--------
Use planning replay generated from real frontier states in the existing corpus.

For each replay record, capture:
  frontier demands
  eligible sources
  provider alternatives
  placements
  current node capacities
  current provider states
  retained artifacts
  deadlines
  network state


Policies
--------
  B2
  B4
  FABLE
  O1 exhaustive checkpoint oracle

Optional ablation:
  Whole-remainder joint planner
  (only include if implementation is easy and result is clear)


Implementation tasks
--------------------
[ ] Add export of replayable checkpoint/frontier state from end-to-end runs.
[ ] Implement deterministic planning replay harness.
[ ] Implement/certify O1 exhaustive enumeration for bounded cases.
[ ] Log exact cost vector for every feasible plan.
[ ] Log oracle gap for selected FABLE plan.
[ ] Add beam-width parameter sweep support.
[ ] Add planner memory/CPU instrumentation.
[ ] Verify hard feasibility is identical between FABLE and O1.
[ ] Verify dominance comparison and stable ranking are deterministic.

Configuration
-------------
Default online beam width:
  K = 8

Suggested sensitivity:
  K = 1, 2, 4, 8, 16, 32

Oracle:
  cap combinations according to current implementation limit
  and clearly report number of oracle-eligible checkpoints

Stress dimensions:
  - number of active hypotheses
  - frontier demands
  - eligible sources
  - provider realizations
  - placements

Do NOT need every Cartesian combination.
Select a compact sweep covering small -> moderate -> worst observed / synthetic-expanded cases.


Headline metrics
----------------
  feasible-plan rate
  deadline miss rate
  predicted/actual checkpoint completion
  oracle gap
  planner p50 latency
  planner p95 latency

Secondary:
  labels generated/pruned
  transferred bytes
  continuation-artifact reuse
  planner memory

-----------------
TABLE 2:
  Planner | Feasible % | Deadline miss % | Completion | Oracle gap | p50 | p95

6. E4 — Real heterogeneous RPi + Jetson Orin + desktop adaptation
======================================================================

Goal
----
Validate FABLE on physically separate heterogeneous nodes and, more
importantly, test whether FABLE adapts when the best physical realization
changes during an ongoing CE.

This is NOT a standalone RQ4.
It is physical validation of RQ3 and, secondarily, RQ1.


----------------------------------------------------------------------
6.1 Physical topology
----------------------------------------------------------------------

Required nodes
--------------
Node A:
  Raspberry Pi
  Intended role:
    sensor/replay endpoint
    lightweight preprocessing/rules if supported

Node B:
  Jetson Orin
  Intended role:
    edge GPU inference
    YOLO/tracking/ReID where appropriate

Node C:
  Desktop PC
  Intended role:
    site-local/cloud-class compute
    heavy inference / cross-camera processing / orchestrator if desired

Network
-------
Connect all nodes through a controllable LAN.

Preferred:
  Linux traffic control (tc/netem) or equivalent on relevant interfaces.

Need the ability to independently apply:
  bandwidth cap
  added latency
  packet loss if needed
  path/interface disable

Clock synchronization
---------------------
[ ] Configure NTP/chrony across all nodes.
[ ] Record clock offset before each campaign.
[ ] Use event timestamps from replay media for CE semantics.
[ ] Use synchronized wall clock only for runtime/latency measurements.


----------------------------------------------------------------------
6.2 Software deployment
----------------------------------------------------------------------

On all nodes:
[ ] Install compatible Docker/container runtime.
[ ] Install FABLE node agent.
[ ] Configure node identity and advertised capabilities.
[ ] Configure MQTT connectivity.
[ ] Configure local retained-data index.
[ ] Configure provider image allowlist.
[ ] Configure resource telemetry.
[ ] Configure heartbeat.

Recommended node IDs:
  rpi_device_01
  orin_edge_01
  desktop_site_01

Controller placement
--------------------
Prefer:
  desktop_site_01

MQTT broker / MongoDB:
  desktop_site_01 unless there is a reason to separate them.

Raw media policy:
  keep raw replay/source data local to the originating node where possible.

----------------------------------------------------------------------

Use existing recorded traces.

6.6 E4a — Compute contention
----------------------------------------------------------------------

Question
--------
When the Jetson becomes resource-constrained during an ongoing CE, can
FABLE choose a new feasible provider/placement while preserving timely
recognition?

Policies
--------
Required:
  B1
  B3
  FABLE

Optional:
  B4

Why B3 is critical:
  B3 tests conventional task-level resource adaptation.
  FABLE additionally determines the instance-specific work set from CE progress.

Perturbation
------------
Start in nominal state.
At a deterministic event-time/wall-time trigger:
  introduce competing GPU/CPU workload on Jetson.

The load MUST be strong enough that:
  - predicted/observed completion changes materially, and ideally
  - the preferred feasible realization changes.

Implementation tasks
--------------------
[ ] Build repeatable load generator.
[ ] Trigger load from experiment manifest at deterministic time/event.
[ ] Advance resource epoch when telemetry crosses configured condition
    or when explicit experiment event is injected.
[ ] Ensure resource-triggered replanning is logged distinctly.
[ ] Verify B1 does not replan.
[ ] Verify B3 can resource-replan the task-level plan.
[ ] Verify FABLE can resource-replan only the current instance frontier.
[ ] Capture before/after selected provider and node.

Suggested metrics
-----------------
  CE preserved?
  deadline met?
  detection delay
  replan/adaptation latency
  provider/node change
  wasted provider work
  transmitted bytes
  CPU/GPU cost

Success criterion
-----------------
At least one workload should exhibit a clearly different physical plan
after contention.

Policies
--------

  B1
  B3
  FABLE

  B4

Metrics

  CE preserved

16. One-sentence expected takeaway from each experiment
======================================================================

E1:
  Event-progress-driven frontier execution avoids broad task-wide evidence
  production while preserving CE recognition.

E2:
  Joint checkpoint planning makes better feasible physical choices than
  fixed or independent greedy frontier realization while remaining close
  to the exhaustive oracle at practical planning latency.

E3:
  CE progress changes which sensors and time intervals are useful, allowing
  FABLE to target downstream sensing and recover bounded historical evidence
  without processing all available data.

E4:
  On real heterogeneous hardware, FABLE changes provider/placement choices
  when compute or network conditions change and preserves CE progress when
  feasible alternatives remain.

E5:
  The centralized semantic/planning control path remains practical across
  the evaluated level of concurrent hypotheses.
