Interpretation
--------------
"Instant" means one event-time transition/observation is matched, not necessarily
that its provider is stateless. A transition such as ENTERS needs at least two
observations. "Interval" means evidence is accumulated over an event-time range.
"Single sensor" means one camera, microphone, or co-located sensor context.
"Cross sensor" means that the implementation explicitly accepts observations from
different sensor IDs. A common world coordinate frame may still require calibration.

The catalog contains both public semantic predicates and intermediate physical
predicates. OBJECT_PRESENT, TRACKS, descriptors, and SAME_ENTITY are normally
provider-chain artifacts used to construct an authored predicate.


AUTHORED PREDICATES AND THEIR PROVIDERS
=======================================

AUDIO_EVENT
  Provider: audio_event_classifier (chain: detect_audio_event).
  Data: mono/multichannel audio_segment.v1 -> audio_event_observation.v1.
  Time: bounded audio windows; thresholding can require consecutive windows and
  uses a refractory interval. Registry match mode is INSTANT_MATCH.
  Space: one audio source. Optional localization/visual association is a separate
  chain and may combine a microphone array with a co-located camera.
  Computation: configurable YAMNet ML inference (16-kHz mono, max/mean pooling
  across YAMNet patches), dependency-light spectral rules, or deterministic test
  backend. The runtime choice is configuration-dependent.
  Packaging: Python code in providers/multimodal/audio.py, normally deployed in
  the fable-multimodal-<node> Docker container. YAMNet model extras are optional.

AUDIO_VISUAL_ASSOCIATION
  Provider: audio_visual_association, preceded by audio_event_classifier and
  gcc_phat_audio_localizer (chain: audio_event_visual_association).
  Data: audio events/localizations plus projected visual tracks/bearings.
  Time: event-time-compatible audio and visual observations in the same window;
  registry match mode is INSTANT_MATCH.
  Space: multimodal and potentially multiple physical sensors, but intended for
  a calibrated/co-located microphone array and camera rather than arbitrary
  cross-camera ReID.
  Computation: GCC-PHAT signal processing for bearing plus deterministic temporal
  and angular compatibility scoring; it does not assert causal identity.
  Packaging: Python code in providers/multimodal, deployed in fable-multimodal.

BOARDS / DISEMBARKS / DEPARTURE_OR_ESCAPE
  Provider: person_vehicle_relation_provider (chain: person_vehicle_transition).
  Data: person and vehicle detection/track sequences.
  Time: multi-frame state machine using stopped-vehicle context, appearance or
  disappearance, proximity/separation, and subsequent vehicle motion/departure.
  The registry exposes the result as an instant transition.
  Space: normally one camera/scene; can consume already projected tracks but does
  not itself perform cross-camera association.
  Computation: rules over YOLO detections and ByteTrack/SORT tracks, not a separate
  learned relation model.
  Packaging: Python provider in the fable-multimodal Docker container; upstream
  YOLO and tracking run in yolo-detector and fable-vehicle containers.

CONVERSATION
  Provider: conversation_provider. Chains:
    conversation_proximity_diarization (no required words), or
    conversation_with_required_content (adds keyword_or_asr_provider).
  Data: visual person tracks, VAD-selected audio, speaker embeddings/turns, and
  optional transcripts when authored terms are required.
  Time: multiple audio frames/windows and sustained person proximity over a
  minimum interval; registry match mode is INTERVAL_MATCH. WebRTC VAD internally
  uses 10/20/30-ms frames; diarization clusters multiple speech segments.
  Space: typically one scene with synchronized camera and microphone. It combines
  modalities but does not itself provide arbitrary cross-camera identity.
  Computation: scale-normalized visual proximity rules; energy or WebRTC VAD;
  model-versioned speaker embeddings; online cosine-cluster diarization; optional
  ASR/keyword model only when content is required.
  Packaging: Python in providers/multimodal, deployed in fable-multimodal. Heavy
  audio-model dependencies are an optional image build extra.

DISTANCE_LT
  Provider: pairwise_distance_evaluator (chain: pairwise_distance_live_vehicle).
  Data: projected_track_set.v1, or same-camera tracks for the explicit nonmetric
  vehicle-scale fallback.
  Time: evaluated over aligned track observations and matched as an interval.
  Space: same camera by fallback; calibrated tracks may share a named world/route
  frame. This provider does not perform ReID by itself.
  Computation: Euclidean/route distance; without calibration, bbox-scale image
  projection is a documented approximation.
  Packaging: Python geometry code in fable-vehicle-<node> Docker containers.

ENTERS / EXITS
  Provider: zone_transition_evaluator after zone_membership_evaluator (chain:
  zone_transition_live_vehicle).
  Data: projected tracks and configured zone/reference geometry.
  Time: at least two membership observations; emits a transition when state
  changes. Registry match mode is INSTANT_MATCH.
  Space: sensor-local when using image geometry, or a calibrated common frame;
  no cross-sensor identity association is performed here.
  Computation: deterministic point-in-polygon/membership and state-transition code.
  Packaging: Python in fable-vehicle Docker; YOLO upstream is a separate container.

FOLLOWS
  Providers: follows_local_geometry or follows_cross_sensor.
  Local chain: follows_local_tracks; retained-data variant:
  follows_local_from_retained_detections. Cross-camera chain:
  follows_cross_camera_reid.
  Data: time-aligned tracks/projections; cross-camera form additionally uses crop
  embeddings, canonical identity associations, and a route graph.
  Time: sustained relative motion/order over multiple frames or track summaries;
  registry match mode is INTERVAL_MATCH. It can also reason about sequential
  sightings rather than requiring both vehicles in every frame.
  Space: local provider needs a single/common coordinate frame. Cross-sensor
  provider explicitly combines two or more cameras through ReID and route/time
  gates; calibration/route information improves the decision but image-space and
  temporal fallbacks exist for uncalibrated data.
  Computation: deterministic relative-motion/ordering rules after YOLO tracking;
  cross-sensor identity uses FastReID/Torchreid/TorchScript embeddings and cosine
  association, with a bounded hosted-VLM fallback when enabled.
  Packaging: Python in fable-vehicle plus identity services; Docker containers are
  yolo-detector-<node>, fable-vehicle-<node>, and fable-identity-x86server.

INSIDE
  Provider: zone_membership_evaluator (chain: zone_membership_live_vehicle).
  Data: projected tracks plus a configured polygon/zone.
  Time: state observation per track snapshot; state can persist across frames.
  Space: one image frame or a calibrated named coordinate frame; not inherently
  cross-sensor.
  Computation: deterministic geometric membership.
  Packaging: Python in fable-vehicle Docker.

MOVING
  Provider: motion_state_evaluator (chain: stopped_live_vehicle also emits STOPPED).
  Data: compact track history from detections/tracking.
  Time: multiple frames are required to estimate displacement/speed, although the
  registry consumes the resulting state observation.
  Space: normally one camera; projected coordinates may be used when available.
  Computation: displacement/speed thresholds over track history.
  Packaging: Python in fable-vehicle Docker.

PASSES
  Provider: pass_reference_evaluator. Chains: passes_live_vehicle, or
  replay_passes_direct for already projected replay tracks.
  Data: tracks/projections and a directed reference line; an image-traversal
  fallback is available when metric calibration is absent.
  Time: a crossing is derived from consecutive/multiple track observations and
  emitted as an instant transition.
  Space: one camera/reference view or a common calibrated frame; not itself a
  cross-camera identity provider.
  Computation: deterministic directed-line crossing and traversal geometry.
  Packaging: Python in fable-vehicle Docker.

PERSON_PROXIMITY / PERSON_PRESENT
  Provider: person_proximity_provider (chain: visual_person_proximity).
  Data: person detections and tracks.
  Time: sustained proximity over multiple frames; both predicates are interval
  observations in the authored registry.
  Space: single camera/image plane. Scale-normalized bbox geometry approximates
  depth when calibration is unavailable.
  Computation: YOLO person detection + tracking + deterministic normalized-distance
  rules; no audio is required.
  Packaging: upstream YOLO container plus Python reasoning in fable-multimodal.

PERSON_ENTERED_BEFORE / PERSON_PRESENT_BEFORE / VEHICLE_PRESENT_BEFORE
  Provider: historical_vehicle_interval_matcher. Chains:
  recover_vehicle_before_audio_event (retained video) and
  recover_vehicle_from_local_segments (retained node-local tracks).
  Data: retained pre-trigger video, detection/track sets, or compact local track
  segments; may produce continuation state for later matching.
  Time: retrospective scan of a bounded event-time interval before a trigger;
  registry match mode is INTERVAL_MATCH.
  Space: fans out across selected nodes where configured. Each node is searched
  locally; cross-camera binding then depends on identity association rather than
  shared geometry.
  Computation: YOLO + tracking + interval matching; vehicle/person embeddings and
  temporal identity gates can bind evidence across cameras.
  Packaging: orchestration code plus yolo-detector, fable-vehicle, and identity
  Docker services.

THREAT_EVENT
  Provider: conversation_provider (same multimodal chain family as CONVERSATION).
  Data: proximity, speech activity/turns, and optionally recognized terms.
  Time: interval evidence; content is computed only when the authored predicate
  requires it.
  Space/computation/packaging: see CONVERSATION.

TRANSFER
  Provider: object_transfer_reasoner, preceded by package_detector and
  interaction_evidence_analyzer (chain: package_transfer_high_resolution).
  Data: high-resolution/full-context images; person, package, and vehicle tracks;
  aligned handoff evidence; retained custody state.
  Time: multiple selected frames and a stable custody change across an interval.
  Space: normally one camera/scene. Cross-camera continuation requires a separate
  identity/continuation association and is not intrinsic to this reasoner.
  Computation: learned object detection (YOLO/full-context filter) followed by
  deterministic interaction scoring and custody-state reasoning.
  Packaging: YOLO detector plus providers/multimodal Python in Docker.

Registry predicates with no direct catalog provider
---------------------------------------------------
FAILED_ATTEMPT_RAPID_EXIT, FORCED_TRANSFER, and SUSPICIOUS_ENTRY appear in the
logical predicate registry (provider families failed_attempt, forced_transfer,
and entry), but providers/registry/catalog.yaml currently contains no provider
that directly declares any of these three predicate names. They therefore need
a rewrite to supported primitives, an external observation source, or a new
provider before they are independently executable.


INTERMEDIATE PROVIDERS USED BY THE CHAINS
=========================================

OBJECT_PRESENT
  Providers: yolo_vehicle_fast_640 (640 px, catalog max 10 Hz),
  yolo_vehicle_balanced_960 (960 px, max 5 Hz), and yolo_full_context_960
  (960 px, max 2 Hz). Each performs single-frame Ultralytics YOLO inference and
  emits detection_set.v1. The current image pins ultralytics 8.3.0 and
  yolov8s.pt (YOLOv8 small), with YOLO_DEVICE=auto for CPU/CUDA selection.
  Portable form: Docker image yolo_detector; model weights are copied/downloaded
  into the image rather than fetched at first inference.

TRACKS
  Provider: multi_object_tracker. Consumes detection_set.v1 and emits track_set.v1
  and track_summary.v1. It is stateful across frames and uses Roboflow ByteTrack
  by default or SORT as a configured alternative (Kalman/assignment-style tracking).
  Portable form: Python provider inside fable-vehicle Docker.

PROJECT_TRACKS
  Provider: camera_projection. Applies camera calibration to each track snapshot
  to produce projected_track_set.v1 in a named world/route frame. Single-sensor
  input, but its common frame enables downstream multi-sensor reasoning.
  Portable form: deterministic Python geometry in fable-vehicle Docker.

EXTRACT_CROPS
  Provider: track_crop_extractor. Selects quality-filtered crops from retained/live
  frames for bound tracks. Current identity flow prefers the corresponding YOLO
  detection bbox rather than a tracker-predicted bbox. Multi-frame selection is
  possible; each crop itself comes from one image.
  Portable form: OpenCV/Python code, normally in detector/identity containers.

VEHICLE_DESCRIPTOR / ENTITY_DESCRIPTOR / GENERAL_VISUAL_DESCRIPTOR
  Providers: vehicle_reid_descriptor, entity_reid_descriptor, and
  openclip_visual_descriptor. Inputs are image crops and outputs are versioned
  embedding sets. ReID can use FastReID vehicle checkpoints, Torchreid person or
  vehicle models, or a supplied TorchScript model. OpenCLIP is a general visual
  descriptor and is explicitly not identity-calibrated by default.
  Time: individual crop inference, usually aggregated across selected track frames.
  Space: sensor-local inference; embeddings are portable across sensors only when
  model/version and preprocessing contracts match.
  Portable form: Python model adapters and model checkpoints in Docker; OpenCLIP
  and some heavy model packages/checkpoints are optional dependencies.

SAME_ENTITY
  Providers: cross_sensor_identity_association and, only as a bounded fallback,
  hosted_vlm_identity_comparator. The local provider uses compatible embeddings,
  cosine distance, time gates, and optional route gates over observations from
  multiple cameras. The VLM provider sends two full detector-boxed frames (rather
  than tiny crops) to a configured hosted OpenAI vision model after local person
  and vehicle ReID remain ambiguous; it is capped at four comparisons per run.
  Time: multi-observation/retrospective association. Space: explicitly cross-sensor.
  Portable form: local Python/model code in fable-identity-x86server Docker; the
  final fallback is an external hosted API and therefore is not fully self-contained.

AUDIO_LOCALIZATION
  Provider: gcc_phat_audio_localizer. Uses a multichannel audio window and known
  microphone geometry to estimate bearing/zone with GCC-PHAT. It spans a signal
  window, is local to one microphone array, and is pure signal-processing code.

SPEECH_ACTIVITY / SPEAKER_DESCRIPTOR / SPEAKER_TURNS / SPEECH_CONTENT
  Providers: voice_activity_detector, speaker_embedding_provider,
  speaker_diarization_provider, keyword_or_asr_provider. They form a staged audio
  pipeline: 10/20/30-ms WebRTC frames (or a whole-window energy baseline), model
  embeddings per speech segment, cosine clustering across segments, then optional
  ASR/keyword work. The ASR/keyword provider is a contract and optional stage; the
  repository does not force one heavyweight ASR model for every deployment.
  Portable form: Python in fable-multimodal Docker, with model extras optional.

Additional internal geometry/state predicates
  STOPPED: motion_state_evaluator, multi-frame track history.
  BEHIND: relative_order_evaluator, route-relative aligned tracks.
  ON_ROUTE: route_map_matcher, projected track snapshot/sequence and route map.
  DWELLS: dwell_evaluator, repeated zone membership for a configured duration.
  ON_ROUTE_SUMMARY: track_summary_route_evaluator over compact continuation state.
  PACKAGE_PRESENT: package_detector, single-frame learned detector/filter.
  TRANSFER_INTERACTION: interaction_evidence_analyzer over several aligned frames.


DEPLOYMENT AND PORTABILITY SUMMARY
==================================

The provider catalog describes portable typed interfaces; the replay runtime file
binds them to existing Docker containers (mode ADOPT_EXISTING):

* yolo-detector-<node>: Ultralytics YOLOv8s single-frame detections, crop/ReID
  dependencies, CPU or CUDA selected by configuration/runtime exposure.
* fable-vehicle-<node>: tracking, projection, zone/pass/motion/distance/follows
  algorithms. Its image installs the repository's [vehicle] Python extra.
* fable-multimodal-<node>: audio, speech, proximity, person/vehicle, and transfer
  providers. Its image installs [vehicle-tracking,multimodal-core], with
  [multimodal-models] only when FABLE_MODEL_EXTRAS=1.
* fable-identity-x86server: centralized cross-camera identity association/ReID.
* hosted VLM fallback: local bounded proxy/provider code plus an external OpenAI
  vision endpoint and OPENAI_API_KEY; not invoked unless local identity cascades
  remain ambiguous and policy/configuration permits it.

Most algorithms also exist as importable Python code and can be unit-tested without
Docker using deterministic fixtures. That does not mean every production ML backend
or checkpoint is installed on the host. Docker is the declared replay/evaluation
portable execution unit; typed JSON/MQTT artifacts are the interoperability boundary.


IMPORTANT LIMITATIONS
=====================

1. Provider capability is not the same as active runtime configuration. YAMNet,
   WebRTC VAD, OpenCLIP, FastReID/Torchreid, ASR, and the hosted VLM are optional or
   selectable. Evaluation manifests/runtime environment determine which is active.
2. Image-space bbox scale/proximity is an approximation, not metric geometry.
   Cross-camera geometry requires calibration or route/location priors; the 2026
   data deliberately relies more heavily on fan-out, temporal, and identity evidence.
3. Tracking IDs are sensor-local. Only SAME_ENTITY/continuation logic may promote
   them to cross-sensor identities.
4. A registry match mode describes how the CE graph consumes an observation. The
   provider may still need several frames/windows to produce that observation.
5. Catalog rates are planning constraints, not guaranteed observed replay rates.
   Actual rate depends on replay speed, source timestamps, compute, and backpressure.
